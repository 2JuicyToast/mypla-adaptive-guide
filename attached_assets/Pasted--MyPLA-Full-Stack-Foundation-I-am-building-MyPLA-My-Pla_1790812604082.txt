# MyPLA — Full-Stack Foundation

I am building **MyPLA (My Planning Assistant)**, an adaptive personal planning assistant.

The repository contains the existing MyPLA frontend framework originally generated by Lovable and exported to GitHub.

## IMPORTANT: PROJECT ROOT

The entire application should live inside:

```text
mypla/
```

Treat `mypla/` as the **working directory/project root**.

The intended structure is approximately:

```text
mypla/
├── src/                  # Existing Lovable React frontend
├── backend/              # Python/FastAPI backend
├── supabase/             # Supabase configuration/migrations
├── tests/                # Python/backend tests
├── .env                  # Local environment variables; NEVER commit
├── .gitignore
├── README.md
└── ...
```

Do not create the Python backend as an unrelated project outside `mypla/`.

Do not move the existing Lovable frontend unless necessary.

# 2. ARCHITECTURE

Use this separation:

```text
Lovable React frontend
        ↓
Python/FastAPI API
        ↓
MyPLA business logic
        ↓
Supabase
        ↓
PostgreSQL
```

### Frontend

Responsible for:

* displaying information
* collecting user input
* triggering actions
* displaying proposals
* displaying confirmations
* displaying schedules/tasks/resources

### Python

Python is the **source of truth for MyPLA's business logic**.

Python should own:

* TaskManager
* PriorityEngine
* Scheduler
* task breakdown
* energy/context logic
* reflections
* resources
* assumptions
* proposals
* approval/commit behavior
* user planning logic
* future AI service interface
* future MyRPG export

### Supabase

Supabase is the persistent backend/data layer.

Use it for:

* PostgreSQL
* persistent task data
* schedules
* reflections
* resources
* user profiles
* future authentication
* future MyRPG data sharing

**Do not put MyPLA's main business logic inside Supabase.**

# 3. SUPABASE PROJECT

A dedicated Supabase project has already been created for MyPLA.

**Do not use the MyCommNet Supabase project.**

The MyPLA Supabase project is separate.

Use environment variables for its connection information.

Expected environment variables include:

```text
SUPABASE_URL=
SUPABASE_PUBLISHABLE_KEY=
```

If a backend-only secret is required later, keep it server-side and never expose it to the React frontend.

**Never commit `.env` to GitHub.**

Add `.env` to `.gitignore`.

Use Replit Secrets/environment variables for deployed development.

Do not hardcode Supabase credentials anywhere in the source code.

---

# 4. SUPABASE DATA API + RLS

The MyPLA Supabase project uses the Data API and Row Level Security.

Use the Supabase publishable key for normal client operations.

RLS must protect user-owned data.

Users should only be able to access their own:

* profile
* projects
* tasks
* task actions
* schedule blocks
* proposals
* coach knowledge
* resources
* reflections

Do not create broad policies such as:

```text
authenticated users can access everything
```

Authentication and authorization are different.

The eventual policy should follow the user's authenticated ID.

Do not use editable `user_metadata` for authorization decisions.

Never expose a Supabase service-role/secret key to the frontend.

```text

tasks

schedule_blocks
proposals
coach_knowledge
resources
reflections
```

* sleep time
* preferences
* created timestamp
* updated timestamp

## projects

Support:

* user ID
* name
* description
* status
* due date
* timestamps

## tasks

Support:

* user ID
* project
* name
* description
* status
* due date
* estimated minutes
* importance
* energy requirement
* category/course
* consequences
* fixed/flexible state
* priority score
* priority explanation
* assistant note
* completed timestamp

## task_actions

Support:

* task
* optional parent action
* name
* description
* status

* position
* timestamps

This must support:

```text

 └── Mission
      └── Smaller Mission
           └── Micro-action
```

## schedule_blocks

Support:

* user
* optional task
* title
* type
* start
* end
* status
* notes

Types should support:

* fixed
* flexible
* break
* routine
* transition

## proposals

This is extremely important.

A proposal is an action suggested by the assistant that has **not yet been committed**.

Support:

* user
* proposal type
* title
* rationale
* proposed changes
* status
* created timestamp
* resolved timestamp

Statuses:

```text
pending
approved
edited
rejected
expired
```

## coach_knowledge

Support:

* user
* topic
* statement
* confidence
* source
* active state
* user correction
* timestamps

Confidence states:

```text
confirmed
observed
suggested
```

## resources

Support:

* user
* name
* type
* URL
* purpose
* when useful
* saved prompt/instructions
* personal note
* tags

This allows MyPLA to remember things like:

> "This AI helped me because it broke my essay into smaller pieces."

and:

> "When I need that again, use this prompt."

## reflections

Support:

* user
* week
* summary
* what went well
* challenges
* helpful strategies
* things worth remembering
* timestamps

This will eventually feed the adaptive priority system.

# 9. PRIORITY ENGINE

Create a deterministic `PriorityEngine`.

**Do not use an LLM for priority calculation.**

Initial score: 0–100.

### Deadline — 45 points

```text
overdue       = 45
today         = 45
tomorrow      = 40
within 3 days = 30
within 7 days = 20
later         = 10
none          = 0
```

### Importance — 30 points

```text
high   = 30
medium = 20
low    = 10
```

### Estimated time — 15 points

```text
≤30 minutes  = 15
31–60        = 12
61–120       = 8
>120         = 4
```

### Energy — 10 points

Compare task energy requirements with the user's current energy.

Energy should influence suitability for the current moment but should not cause an unimportant task to automatically outrank a critical deadline.

The scoring weights must be easy to change later.

Return:

```text
score
explanation
```

# 14. PROPOSAL / APPROVAL SYSTEM

This is a fundamental MyPLA feature.

The future AI must NOT directly modify important application state.

The architecture is:

```text
Assistant
   ↓
Proposal
   ↓
User sees proposed change
   ↓
Approve / Adjust / Reject
   ↓
Python commits the change
```

This applies to things like:

* moving tasks
* changing schedules
* creating actions
* breaking tasks down
* changing estimates
* changing priorities
* recommending resources

The proposal system must be real backend infrastructure even before the AI exists.
